# GitHub App 認証の設計判断

Claude Code からの GitHub 操作を、個人アカウントではなく **GitHub App** として
行うための設計記録。タスク6（PR #7）で実装・レビューを経て確定した内容。

**このドキュメントの使い方**: 同種の構成を新しいプロジェクトで作るときに、
最初にこれを読む。特に「却下した案」の節は、同じ提案を再検討しないために
必ず目を通すこと。実装は `scripts/` の4ファイルを出発点にできる。

| ファイル | 役割 |
| --- | --- |
| `scripts/github-app-auth.ts` | インストールトークンの発行・キャッシュ |
| `scripts/git-credential-github-app.sh` | git の HTTPS 認証（credential helper） |
| `scripts/with-github-app.sh` | gh の実行ラッパー（許可リスト方式） |
| `scripts/gh-review-reply.sh` | レビュースレッド返信の専用スクリプト |

---

## 1. 採用した設計判断

### 1-1. git はラッパーで包まない。credential helper を使う

**Do**: git の認証は credential helper で差し替え、`git` 自体は素で実行する。

**理由**: ラッパーで包むと Claude Code の deny リストの照合が壊れる。
`.claude/settings.json` の `Bash(git push:*--force*)` は、
`scripts/with-github-app.sh git push --force` という**先頭が別コマンドの
文字列には一致しない**。つまりラッパーを挟むだけで既存のガードレールが
無効化される。credential helper なら Claude は素の `git push` を実行するので、
deny がそのまま効く。

### 1-2. 引数から意図を推測しない。入力の形を絞る

**Don't**: 引数を解析して「この呼び出しは危険か」を判定する。

**Do**: 受け付ける入力の形自体を狭くする。実装では次の3つ。

- ラッパーは **`gh` のみ**実行できる（`git` も `sh -c` も不可）
- 引数は**ロングオプションのみ**（`-` に英字が続く引数は一律拒否）
- **許可リスト方式**（default-deny）。許可した gh サブコマンド以外は拒否

**理由**: 詳細は「却下した案」2-1 を参照。要約すると、CLI の引数は結合フラグ・
値の連結・URL フラグメント等でいくらでも変形でき、判定は**取りこぼしと誤検知を
交互に起こす**。しかも判定に必要なオプション表は CLI のバージョンで変わる。

### 1-3. 書き込みは専用スクリプトで、URL とメソッドを自分で組み立てる

**Do**: 書き込みが必要な操作は、汎用 API コマンドを許すのではなく専用
スクリプトを用意する。`scripts/gh-review-reply.sh` がその例。

- 宛先は `origin` から導出する（呼び出し側が指定できない）
- ID の類は数字のみ許可する（パス差し込みの防止）
- 本文は JSON として渡す（フラグとして解釈されない）

**Do**: 汎用の `gh api` は**読み取り専用**に固定する。メソッドや本文を
指定しうるフラグ（`--method` / `--field` / `--raw-field` / `--input`）が
1つでもあれば拒否する。これらが無ければ必ず GET になるので、
宛先を問わず書き込みは発生しない。

### 1-4. 認証に失敗したら fail closed

**Do**: credential helper はトークンを取得できないとき `quit=1` を返す。

**理由**: helper が単に失敗（非ゼロ終了）すると、git は後続の helper や
`GIT_ASKPASS`・対話入力へ進み、**個人アカウントの資格情報で push が成功して
しまう**。それでは操作主体を分離した意味がない。`quit=1` を返すと git は
以降の helper も対話も行わずに中断する。

**Do**: エラーの原因（`.env` 未設定、秘密鍵の不備）は stderr に出す。
credential helper のプロトコルは stdout の `key=value` なので、stderr は
壊さない。握り潰すと利用者は git の一般的な認証エラーしか見えなくなる。

### 1-5. 「認証主体が変わる経路」を潰す

トークンを注入しても、次の経路では**別の主体で実行されてしまう**。
いずれも通常の引数・環境変数だけで成立し、ファイルの配置を必要としない。

| 経路 | 何が起きるか | 対処 |
| --- | --- | --- |
| `--web` | ブラウザにログイン中の個人アカウントで PR / コメントが作られる | 拒否 |
| `--editor` | 外部エディタが `GH_TOKEN` を継承して起動する | 拒否 |
| `Authorization:` ヘッダ | 注入したトークンより優先され個人認証になる | 拒否 |
| `GIT_CONFIG_PARAMETERS` | `GIT_CONFIG_COUNT` より優先。`extraheader` の注入も可能 | unset |
| `GIT_DIR` | `git -C` より優先。別クローンの origin を読ませられる | unset |

**Do**: フラグの拒否だけに頼らず、**外部プロセスの起動先そのものを無害化**
してから exec する。

```bash
export GH_EDITOR=false EDITOR=false VISUAL=false GIT_EDITOR=false
export GH_BROWSER=false BROWSER=false
export GH_PAGER=cat PAGER=cat
```

**理由**: フラグの判定は結合形や値の連結で取りこぼしうる（2-1 参照）うえ、
gh はエディタ以外にページャやブラウザも子プロセスとして起動する。
判定漏れがあっても外部プロセスが実行されないよう、**起動先そのものを潰す**。
フラグ判定は「分かりやすいエラーを出す」ためのものと位置づける。

**外部エディタが起動する経路の正確な整理**（gh 2.x で確認）:

| 呼び出し | 挙動 |
| --- | --- |
| `gh pr comment` に本文フラグなし | **対話プロンプト**が出る（エディタが直接起動するわけではない） |
| `gh pr comment -e` / `--editor` | プロンプトを飛ばして**外部エディタを起動** |

環境変数の無害化が潰すのは**エディタ／ブラウザ／ページャの起動先**であって、
対話プロンプトそのものではない。なお Claude Code のような非 TTY 実行では
対話プロンプトは成立せず失敗する。

### 1-6. App 権限は最小化する

**Do**: `contents: write` / `pull_requests: write` / `metadata: read` のみ。

**Don't**: `workflows` を付けない。付けると `.github/workflows/` を書き換えて
CI 経由で secrets を抜く権限昇格が成立する。**外すと GitHub 側がその push を
拒否する**ので、スクリプトの判定ではなくサーバー側で強制される。

`actions` も read までに留める（実行ログの削除は痕跡を消せる）。

### 1-7. シェルスクリプトの定型

**Do**: `cd` を含むコマンド置換は `CDPATH=` を付ける。

```bash
SCRIPT_DIR="$(CDPATH= cd -- "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
```

**理由**: `CDPATH` が export されていると `cd` が解決先を stdout に出力し、
コマンド置換に混入する。**トークンを取得するコマンド置換で起きると、
トークン文字列が壊れて credential helper のプロトコルが破綻する。**

## 2. 却下した案と、なぜ破綻したか

同じ提案が繰り返し出るので、理由まで含めて記録する。

### 2-1. ラッパーが引数を解析して危険な操作を弾く方式

**却下**。レビューで次の順に穴が見つかり、修正のたびに別方向の穴が開いた。

| 見つかった穴 | 修正 | その修正で開いた穴 |
| --- | --- | --- |
| `gh -R o/r pr merge`（フラグ位置） | フラグを読み飛ばす | — |
| `gh alias` 経由（`gh m`） | 許可リスト方式へ | — |
| `-XDELETE`（値の連結） | 連結形も見る | — |
| `-iXDELETE`（結合クラスタ） | クラスタを分解 | — |
| `--input -XGET`（値をメソッドと誤認） | 値を消費してから解析 | — |
| `-dw` / `-de`（bool の結合） | 結合形も拒否 | `-bFixed` を誤検知 |
| `-bFixed` の誤検知 | 完全一致に狭める | `-dw` を再び取りこぼす |

**根本原因**: 引数の見た目から「フラグか値か」を判定するには CLI の
オプション表が必要で、その表は CLI のバージョンで変わる。判定は
**取りこぼしと過剰拒否を交互に起こし、収束しない**。

**代わりに採ったもの**: 入力の形を絞る（1-2）。ロングオプションのみにすると
`-w` / `-dw` は自動的に不可になり、`-bFixed` も「短縮フラグは使えません」
という**正しいメッセージ**で拒否される（誤検知ではなくなる）。

### 2-2. `gh api` に書き込みを許し、危険な宛先・メソッドを弾く方式

**却下**。同じ理由で破綻した。

- `PUT /git/refs/... -F force=true` → force push の deny を迂回できる
- `POST /repos/o/r/merges` → 許可外のマージ
- `gh api graphql` → mutation で何でもできる
- `.../feature#/pulls/1/comments` → `#` 以降はサーバーに送られないので、
  許可パターンに一致させつつ実リクエストは別の宛先にできる

宛先の許可リストを作っても、URL の正規化（クエリ・フラグメント）まで
自前で行う必要があり、やはり収束しない。

**代わりに採ったもの**: `gh api` は読み取り専用に固定し、書き込みは専用
スクリプトへ（1-3）。**判定する対象そのものを無くす。**

### 2-3. `gh` / `npm` の実行パスを絶対パスに固定する

**却下**。前提が成立する時点でラッパーを迂回する必要がない。

`PATH` を書き換えて偽バイナリを置ける相手は、このユーザー権限で任意コードを
実行できる。その相手は `~/.config/github-apps/*.pem` を直接読めるし、
**`with-github-app.sh` 自体を書き換えられる**。スクリプトは自分を呼び出す
主体に対するセキュリティ境界にはなり得ない。

加えて `gh` は `/opt/homebrew/bin` / `/usr/local/bin`、`npm` は asdf / nvm /
Volta などで場所が大きく異なり、**利得なしに可搬性だけを失う**。

### 2-4. deny リストの穴をこのタスクで塞ぐ

**却下（別タスク化）**。`git push origin +HEAD:refs/heads/x` の `+`（強制更新）は
現在の deny が捕捉しないが、これは **App 化以前から存在する穴**で、App 化で
新たにできるようになったことはない。また 1 行追加では済まず、部分一致ベースの
パターン全体（取りこぼしと過剰拒否の両方）の棚卸しが必要。
本リポジトリではタスク7として切り出した。

## 3. この設計で防げないこと

**明示しておかないと、レビューが際限なく厳しい前提へ寄っていく。**

### 3-1. ローカルで任意コード実行できる攻撃者

秘密鍵はファイル権限（`0600`）でしか守られていない。**同じユーザー権限で
動くプロセスは `.pem` を読めるので、ラッパーを介さずトークンを無期限に
発行できる。** マシンが侵害された時点で App も侵害されている。
復旧手段は App 設定での鍵の失効・再生成。

### 3-2. グローバル git 設定による上書き

次の設定があると、credential helper は**呼ばれずに**個人の資格情報で
操作される。ラッパーを通さない素の `git push` にも効くため、
スクリプト側では防げない。**セットアップ時の確認事項とする。**

```bash
git remote get-url origin            # user:token@ が含まれていないこと
git config --get-regexp extraheader  # 何も出ないこと
```

### 3-3. 完全な引数解析

`-wL5` のように bool と値連結を混ぜた形は、どんな構文ルールでも
捕まえきれない。だから安全性はフラグ判定ではなく環境の無害化に置く（1-5）。

### 3-4. 本当の防壁はどこか

ラッパーと deny リストは「**誤誘導されたエージェントの誤操作**」に対する
多重防御であって、最終的な壁ではない。実効的な防御は順に:

1. **`main` のブランチ保護**（サーバー側。ローカルの細工では破れない）
2. **App 権限の最小化**（サーバー側で強制。特に `workflows` を外すこと）
3. **トークンの短寿命（約1時間）と、鍵をいつでも失効できること**
4. ラッパー / deny リスト（多重防御）

## 4. `AGENTS.md` に貼る脅威モデルの雛形

**新しいプロジェクトでは最初にこれを `AGENTS.md` に入れること。**
これが無いと、レビュアー（Codex 等）の指摘が徐々に「攻撃者が既にマシンで
任意コード実行できる」前提へエスカレートし、原理的に対応不能な指摘に
時間を溶かす。実際にタスク6ではその往復が10ラウンド以上発生した。

```markdown
## 脅威モデル（レビュー時の前提）

このリポジトリのスクリプトは、GitHub 操作の**主体**を個人アカウントから
GitHub App に分離するためのものです。レビューは以下の前提で行ってください。

### 想定する脅威
- プロンプトインジェクション等で誤誘導されたエージェントが、通常の想定経路で
  意図しない GitHub 操作を行うこと
- 通常の引数・環境変数だけで認証主体が別のものに変わってしまうこと

### 想定しない脅威（対応範囲外）
- ローカルで任意コードを実行できる攻撃者
  （秘密鍵を直接読めるため、スクリプトでは原理的に防げない）
- 利用者自身のグローバル設定による上書き（セットアップ時の確認事項とする）

### 最終的な防壁
ブランチ保護 / App 権限の最小化 / トークンの短寿命と鍵のローテーション。
スクリプトのガードはこれらの内側にある多重防御であり、単独の防壁ではない。

### 指摘の優先度
上記「想定する脅威」に該当するもの、または完成条件を満たしていないものを
優先してください。それ以外は優先度を下げて構いません。
```

## 5. 検証済みの範囲 / 未検証の項目

### 検証済み

- macOS（ローカルのノート PC）、単一ユーザー
- 単一リポジトリへの App インストール
- 対話セッションの Claude Code
- git は HTTPS リモート

### サーバー版で再検討が必要（未検証）

| 項目 | 論点 |
| --- | --- |
| 秘密鍵の置き場所 | `~/.config/*.pem` は使えない。シークレットストア／マウント／環境変数のどれか。`GITHUB_APP_PRIVATE_KEY_PATH` の代わりに鍵本体を環境変数で受ける口が要る |
| `.env` の扱い | プラットフォームの環境変数注入に置き換わる。`dotenv` 依存は残すか |
| ヘッドレス実行 | 対話入力が無い前提。fail closed の挙動（`quit=1`）がそのまま妥当か |
| 複数リポジトリ | 1インストールで複数リポジトリを扱う場合、`gh-review-reply.sh` の「宛先は origin 固定」という前提が変わる |
| キャッシュの排他制御 | 現在のトークンキャッシュに**ロックが無い**。同時実行があると読み書きが競合しうる |
| credential helper の登録 | クローンごとの `git config` は自動化が要る（コンテナなら起動時に実行） |
| deny リスト | ヘッドレスの Claude Code では設定が異なる。ガードレールの前提を組み直す必要がある |

### 次にやること

サーバー版が動いたら、ローカル版と**共通する部分**が本当に再利用可能な
設計である。その時点で Skill 化を検討する（1事例だけで Skill にすると、
未検証の前提を固定してしまう）。
